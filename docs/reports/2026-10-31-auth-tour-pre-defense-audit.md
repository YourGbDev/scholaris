# Pre-defense auth and Ari tour audit

Date: 2026-10-31, Asia/Manila. Audited revision: `1804904` (Build 17), following `5f939d5`.

User direction: inspect and plan before execution; work solo without five agents. No product code, dependencies, branch, worktree, release number or IPA was changed by this audit. The supplied physical-iOS observations are evidence of user-visible behavior, not a reproduced native trace in this environment.

## Workstream A: confirmed source findings

1. **The student tab index is not session scoped.** `HomeTabIndexNotifier.build()` in `lib/features/home/presentation/home_screen.dart` returns zero only at provider initialization. It does not watch `currentUserIdProvider`; the non-auto-disposed notifier survives Home unmounting. The Settings logout handler only calls Supabase sign-out. A normal login does not reset the tab. The router resets Home only after profile setup, and its `/profile`, `/tracker`, and Discover shortcuts also schedule independent tab-setting microtasks. This directly explains the stale Profile destination inside Home after reauthentication.
2. **The reported imperative-success-navigation race is not confirmed.** `LoginScreen._onLogin()` awaits CAPTCHA and `signInWithPassword`, but has no success `context.go('/home')`. Its imperative navigation is the unconfirmed-email error case, which should remain. Removing a nonexistent success push cannot fix the flicker.
3. **Auth/profile readiness has multiple refresh inputs.** `AuthSessionNotifier` and `routerProvider` each subscribe separately to raw Supabase events. The router also refreshes for profile completeness, role, onboarding, intro and splash. `ProfileCompleteNotifier` separately calls `ProfileRepository.fetchCurrent()`, while role awaits `currentProfileProvider`, producing two profile reads with independent completion/error timing. `authRedirectDecision(profileLoading: true)` holds the current route by returning null. Login's `finally` unlocks the form as soon as the auth request returns, without waiting for route readiness. These are concrete timing weaknesses; they do not by themselves prove the exact Login → Profile → Login → Home sequence. A route observer and controllable delayed auth/profile responses must distinguish actual navigation from overlapping transition frames before that sequence is claimed reproduced.
4. **Home renders mixed loading snapshots.** `StudentDashboardScreen.build()` falls back from `dashboardAsync.valueOrNull` to an all-zero `DashboardInfo`, while In Progress separately reads `applicationsProvider` and Saved/Closing Soon come from the aggregate. Previously retained async values can also be read during recomputation. No hardcoded `1 / 0 / 1` fallback was found. The mixed-source/zero-fallback implementation explains the opportunity for hydration pops, but the exact reported values have not been reproduced.
5. **An additional draft isolation gap exists.** `applicationDraftProvider` is a non-auto-disposed family keyed only by scholarship ID. Its `ApplicationDraftNotifier.build()` watches no user identity. The actual scholarship materials widget reads/writes this provider for essay/recommender input. Therefore the in-memory draft is not isolated between accounts opening the same scholarship. Existing auth-boundary draft tests cover profile-setup drafts, not this application draft. Bookmark/application mutation methods also need delayed-completion tests: a user dependency on `build()` alone does not prove that a manually assigned state after `await` belongs to the current session.

## Workstream A: CAPTCHA findings

- `captcha_view_native.dart` constructs its WebView without setting a background color. It exposes the WebView immediately after `loadRequest()` returns, without an explicit page/widget-ready state or covering placeholder. This is consistent with the reported first-frame flash, but native compositor behavior still needs device verification.
- `web/captcha_challenge.html` sets neither a forced light widget theme nor a light page color scheme/background. Appending `?theme=light` alone would not work with this script: it currently reads only `key` and `nonce` and passes no theme into `turnstile.render`.
- The bridge recognizes nonce-bound token/error messages, not readiness. The HTML has a 15-second timer starting before the external SDK is ready. Loading timeout and human-interaction lifetime should be distinguished; cancellation, error, expiry and token delivery must remain fail-closed and terminal once.
- The repository page and deployed HTTPS challenge page must both be updated/verified before a new IPA can demonstrate the theme fix. The deployed page was not inspected or changed during this audit. An API-ready signal must not be represented as proof that a cross-origin widget has painted or that a human has verified.

## Workstream B: confirmed source findings

1. **No scroll presentation lifecycle exists.** `StudentApplicationGuide._onScroll()` only measures geometry/readiness. The painter, note and cue remain rendered at full opacity during user scroll. `_bubble()` can occupy 210 px plus its exterior hint, falling back to 110 px above the bottom. This obstructs content as reported.
2. **Scrolling is intercepted, not naturally forwarded.** The guide's full-surface `GestureDetector` translates drag deltas into `_scrollBy()` → `ScrollController.jumpTo()`. The underlying tour pages are intentionally `IgnorePointer`/`ExcludeFocus`/`ExcludeSemantics` to prevent real actions. Removing these protections to get scrolling would expose upload/submission/navigation actions. Jump-driven scrolling also differs from native drag/fling physics.
3. **A listener inside the overlay cannot observe its sibling pages.** Home already has a per-tab `NotificationListener<ScrollNotification>` for the floating dock, while `StudentTourLayer` is a sibling in the shell Stack. A new notification listener only around the guide would miss the real Home/Discover/Profile list notifications. Those must be forwarded from their ancestor; local detail/review notifications can be observed around the guide's own page subtree.
4. **Discover's full-feed requirement is explicit.** Its stop sets `end: true`; `_measure()` requires the actual end helper card plus `extentAfter <= 24`. This was the previous approved rule to prevent premature advancement. The new physical-device feedback changes that requirement for Discover; it is not an accidental timer bug. Preserve meaningful detail/review milestones rather than applying a short generic distance to every page.
5. **Button-only geometry is explicit.** Discover passes `detailsGuideKey` into `ScholarshipCard.viewDetailsKey`, placed on the 44 px View Details control. `_anchor`, `_schedule`, `_measure` and `_SpotlightPainter` use that single rectangle both for the cutout and permitted action. `_show(7)` jumps Discover to zero, then `ensureVisible(alignment: .2)` targets the button. There is no separate card target. The cutout also uses a 16 px corner radius rather than the current card radius of 26 px.

## Recommended decisions

- Preserve router-owned success navigation. Subscribe its refresh path to the reactive auth boundary rather than maintaining another raw Supabase listener. Use the same profile fetch for role/setup decisions. Prove the timing with route-transition tests before changing animations.
- Reset the tab on real user/session boundaries without haptics; do not reset on token renewal, ordinary profile refresh or a normal in-session tab visit. Preserve authorized role routing, recovery, setup and deliberate deep links. Guard stale tab-setting microtasks and async completions.
- Gate landing on current-user profile/role resolution, not an unbounded wait for every scholarship/bookmark request. Prefetch summary data; show neutral count placeholders until a complete same-session summary is available. Keep explicit retry/error behavior. An authenticated user must not be sent back to Login solely because a data fetch failed.
- Force light CAPTCHA rendering and provide an initial white/transparent native surface plus a covering loading placeholder until the page's own initialization signal. Preserve nonce/origin/path validation, one-shot delivery and CAPTCHA-enabled release rules. Verify first paint on iPhone.
- Hide the scrim, note, cue and their invisible hit targets during browsing: 150 ms fade out, restore after a 350 ms settled-scroll debounce. Keep Skip/Back available. Cancel work on step/account changes and disposal. Reduced motion uses immediate presentation changes.
- Discover completion becomes net user-driven progress of `min(400 px, remaining extent at step entry)`; short/non-scrollable content has a valid completion path. Programmatic alignment, resize and jiggle travel must not count. After settling, show a continue prompt; **do not auto-open a scholarship or auto-advance while the student is browsing**.
- Add separate full-card and View Details targets. Position the real selected card, spotlight its visible card outline, and allow only the actual button rectangle to advance. Keep one frozen scholarship throughout detail/review. If the full card is taller than the usable viewport, preserve text size, use a clipped card spotlight and a compact note outside its action area.
